# Learning Guide: T001.1.3 - Windows Bridge Directory Structure

## What is the Windows Bridge?

The **Windows Bridge** is a critical component in the ContPAQ-Win architecture that serves as the intermediary between the modern web-based Desktop App and the Windows-native ContPAQi accounting software.

## Why Do We Need It?

ContPAQi uses **COM (Component Object Model)** technology for its SDK, which is a Windows-only technology. Since our Desktop App uses Electron/React (JavaScript-based), it cannot directly communicate with COM objects.

The Windows Bridge solves this problem by:
1. Running as a native Windows service written in C#/.NET
2. Exposing a REST API that Electron can call
3. Internally using COM interop to communicate with ContPAQi

```
┌─────────────────┐     HTTP/REST     ┌─────────────────┐     COM      ┌─────────────────┐
│   Desktop App   │ ◄───────────────► │  Windows Bridge │ ◄──────────► │   ContPAQi SDK  │
│ (Electron/React)│                   │    (C#/.NET)    │              │                 │
└─────────────────┘                   └─────────────────┘              └─────────────────┘
```

## Directory Structure Explanation

```
windows-bridge/
└── src/
    └── .gitkeep
```

### `windows-bridge/`
The root directory for all Windows Bridge related code and configuration.

### `windows-bridge/src/`
Contains the C# source code. This will eventually include:
- **Controllers/** - REST API endpoints
- **Services/** - Business logic and ContPAQi integration
- **Models/** - Data transfer objects (DTOs)
- **Interop/** - COM wrapper classes for ContPAQi SDK

### `.gitkeep`
A convention file used to track empty directories in Git. Git doesn't track empty directories, so we add this placeholder file.

## Technology Choices

### Why C#/.NET?
- **Native COM support**: C# has built-in COM interop capabilities
- **Windows service support**: Easy to create Windows services
- **Performance**: Compiled language with good performance
- **ContPAQi compatibility**: Many ContPAQi integrations use C#

### Why a Separate Service?
- **Process isolation**: If the COM calls crash, they don't crash the entire app
- **Security**: Can run with different permissions than the user
- **Background operation**: Can run even when the UI is closed
- **NSSM management**: Easy restart and monitoring

## Testing Approach

We use TDD (Test-Driven Development) even for infrastructure:

1. **Write tests first** - Define what the directory structure should look like
2. **Run tests (Red)** - Tests fail because directories don't exist
3. **Implement** - Create the directories
4. **Run tests (Green)** - Tests pass, proving implementation is correct

This approach ensures:
- We don't forget required directories
- Documentation of the expected structure
- Regression detection if someone accidentally deletes directories

## Key Concepts

### COM (Component Object Model)
A Microsoft technology that allows different programs to communicate. ContPAQi exposes its functionality through COM interfaces.

### REST API
A standard way for web applications to communicate. Our Windows Bridge exposes endpoints like:
- `GET /api/companies` - List available companies
- `POST /api/documents` - Post an invoice to ContPAQi

### Windows Service
A background process that runs on Windows without user interaction. Managed by the Windows Service Control Manager (SCM) or tools like NSSM.
