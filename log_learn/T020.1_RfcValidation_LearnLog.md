## Concepts Learned

### 1. Mexican RFC Structure
Learned about Mexican tax identification number (RFC - Registro Federal de Contribuyentes):

**Persona Física (Individual)** - 13 characters:
```
GODE561231GR8
└┬─┘└──┬──┘└┬┘
 │    │    └─ Homoclave (verifier digits)
 │    └────── Date of birth (YY-MM-DD)
 └─────────── Name initials (4 chars from paternal, maternal, first name)
```

**Persona Moral (Company)** - 12 characters:
```
SAT970701NN3
└┬┘└──┬──┘└┬┘
 │   │    └─ Homoclave
 │   └────── Constitution date
 └────────── Company name initials (3 chars)
```

### 2. TypedDict for Return Types
Used `TypedDict` for structured return values from validation function:

```python
from typing import TypedDict, Optional

class RfcValidationResult(TypedDict):
    """Result of RFC validation."""
    valid: bool
    rfc_type: Optional[str]
    normalized_rfc: Optional[str]
    error: Optional[str]
```

Benefits:
- Type hints for dictionary keys
- IDE autocomplete
- Static type checking support
- Clear documentation of expected structure

### 3. Validation as Pure Function
Designed `validate_rfc()` as a pure function that returns a result dict rather than raising exceptions:

```python
def validate_rfc(rfc: str) -> RfcValidationResult:
    if not rfc:
        return RfcValidationResult(
            valid=False,
            rfc_type=None,
            normalized_rfc=None,
            error="El RFC no puede estar vacío",
        )
    # ... more validation
    return RfcValidationResult(
        valid=True,
        rfc_type="persona_fisica",
        normalized_rfc=normalized,
        error=None,
    )
```

Benefits:
- No exception handling needed in caller
- Always returns structured data
- Easy to serialize for API response
- Testable without try/catch

### 4. Regex with Mexican Characters
Used regex patterns that support Ñ and & (encoded in RFC):

```python
# Persona Física: 4 letters + 6 digits + 3 alphanumeric
RFC_PERSONA_FISICA_PATTERN = re.compile(r"^[A-ZÑ&]{4}[0-9]{6}[A-Z0-9]{3}$")

# Persona Moral: 3 letters + 6 digits + 3 alphanumeric
RFC_PERSONA_MORAL_PATTERN = re.compile(r"^[A-ZÑ&]{3}[0-9]{6}[A-Z0-9]{3}$")
```

Note: In Mexican RFC encoding:
- `&` represents "y" (and) in company names
- `Ñ` represents "ñ" in names

### 5. Date Validation in RFC
The RFC date portion (YYMMDD) requires validation:

```python
def _validate_date_portion(date_str: str) -> tuple[bool, str]:
    year = int(date_str[0:2])   # Any 2-digit year is valid
    month = int(date_str[2:4])  # Must be 01-12
    day = int(date_str[4:6])    # Must be valid for month

    days_in_month = [31, 29, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31]
    max_days = days_in_month[month - 1]

    if month < 1 or month > 12:
        return False, "El mes debe estar entre 01 y 12"
    if day < 1 or day > max_days:
        return False, f"El día debe estar entre 01 y {max_days:02d}"
    return True, ""
```

### 6. Validation vs Error Endpoints
Design decision: Return 200 with validation result rather than 4xx for invalid data:

```python
@router.post("/validate/rfc", response_model=RfcValidationResponse)
async def validate_rfc_endpoint(request: RfcValidationRequest) -> RfcValidationResponse:
    result = validate_rfc(request.rfc)
    return RfcValidationResponse(
        valid=result["valid"],
        rfc_type=result.get("rfc_type"),
        # ...
    )
```

Rationale:
- Client explicitly asked for validation (not trying to create a resource)
- Invalid RFC is expected use case, not an error
- 422 is for malformed requests (missing rfc field)
- Consistent API behavior

## Best Practices Identified

1. **Error messages in Spanish**: For Mexican accountant users
2. **Normalize input**: Uppercase, trim whitespace
3. **Return normalized value**: Let client use clean version
4. **Separate validation logic**: Pure function, not in endpoint
5. **Comprehensive tests**: Cover all RFC patterns and edge cases
