# T025.2 - Vendor Resolution Flow Learnings

**Task**: Implement vendor resolution flow
**Date**: 2025-12-18

## Key Learnings

### 1. Form State with useEffect Reset

When a modal's initial values come from props, reset state when modal opens:

```tsx
const [name, setName] = useState(suggestedName);

// Reset form when modal opens with new data
useEffect(() => {
  if (isOpen) {
    setName(suggestedName);
    setCommercialName('');
  }
}, [isOpen, suggestedName]);
```

This ensures:
- Fresh values when modal reopens
- No stale state from previous usage
- Optional fields get cleared

### 2. Controlled Form Components

For accessible forms, use controlled inputs with proper labeling:

```tsx
<label htmlFor="vendor-name">
  Nombre del Proveedor <span className="text-red-500">*</span>
</label>
<input
  id="vendor-name"
  type="text"
  value={name}
  onChange={(e) => setName(e.target.value)}
  disabled={isLoading}
/>
```

Benefits:
- `htmlFor` associates label with input for screen readers
- Clicking label focuses input
- `id` must match `htmlFor` value

### 3. Form Validation Pattern

Simple client-side validation without a library:

```tsx
const isNameValid = name.trim().length > 0;

<button
  type="submit"
  disabled={isLoading || !isNameValid}
>
  Crear Proveedor
</button>
```

And in the handler:

```tsx
const handleSubmit = (e: React.FormEvent) => {
  e.preventDefault();
  if (name.trim()) {
    onSubmit({
      rfc,
      name: name.trim(),
      commercialName: commercialName.trim() || undefined,
    });
  }
};
```

### 4. Optional Field Patterns

Mark optional fields clearly:

```tsx
<label>
  Nombre Comercial{' '}
  <span className="text-gray-400 text-xs">(opcional)</span>
</label>
```

And handle in submission:

```tsx
commercialName: commercialName.trim() || undefined,
```

Using `undefined` instead of empty string helps with API calls.

### 5. Read-Only Display vs Input

For data that shouldn't be edited (like RFC), use styled div instead of disabled input:

```tsx
<div className="bg-gray-100 px-3 py-2 rounded-md text-gray-900 font-mono">
  {rfc}
</div>
```

Benefits:
- Clearer visual distinction from editable fields
- No accidental editing
- Better for screen readers (not announced as "text field")

### 6. Testing Multiple Text Occurrences

When text appears multiple times (like RFC in both message and display):

```tsx
// Don't use getByText which expects single match
expect(screen.getByText('RFC')).toBeInTheDocument();

// Use test IDs for specific elements
const rfcDisplay = screen.getByTestId('rfc-display');
expect(rfcDisplay).toHaveTextContent('ABC123456789');
```

### 7. Blue vs Orange Color Schemes

Different modal purposes use different colors:
- **Orange**: Warning modals (DuplicateWarningModal)
- **Blue**: Creation/action modals (CreateVendorModal)

This follows common UX patterns:
- Orange = caution, reconsider
- Blue = action, proceed

### 8. Vendor Resolution in ContPAQi Context

In Mexican accounting software:
- RFC is the unique identifier (like SSN for businesses)
- Name must match official registration ("razón social")
- Commercial name is the public brand name
- ContPAQi requires vendor to exist before creating entries

## Integration Considerations

The modal component handles UI only. Integration requires:

```tsx
const handleVendorResolution = async (rfc: string, suggestedName: string) => {
  // 1. Check if vendor exists
  const vendor = await bridgeClient.getVendorByRfc(rfc);

  if (vendor) {
    // 2a. Vendor found - proceed
    return vendor;
  }

  // 2b. Show create modal
  setShowCreateVendor(true);
  setVendorRfc(rfc);
  setSuggestedName(suggestedName);

  // Wait for user action...
};

const handleCreateVendor = async (data: CreateVendorData) => {
  setIsCreating(true);
  try {
    const vendor = await bridgeClient.createVendor(data);
    setShowCreateVendor(false);
    // Continue with entry creation
  } catch (error) {
    setVendorError(error.message);
  } finally {
    setIsCreating(false);
  }
};
```
